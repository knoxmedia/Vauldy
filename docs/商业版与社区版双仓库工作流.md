# 商业版与社区版双仓库工作流

**文档版本**：v1.0
**编写日期**：2026-07-06
**适用仓库**：knox-media（商业版） ↔ Vauldy（社区版）

---

## 1. 仓库概述

| 仓库 | GitHub 地址 | 定位 | 许可 |
| ---- | ----------- | ---- | ---- |
| **knox-media** | `github.com/knoxlab/knox-media.git` | 商业版（私有），包含全部社区版功能 + 商业模块（预转码、License 等） | Proprietary |
| **Vauldy** | `github.com/knoxmedia/Vauldy.git` | 社区版（公开），核心媒体管理功能，MIT 开源 | MIT |


## 2. Git Remote 配置

knox-media 本地仓库配置两个 remote：

```
origin    → github.com/knoxlab/knox-media.git   (商业版，私有)
upstream  → github.com/knoxmedia/Vauldy.git     (社区版，公开)
```

**配置命令**：

```powershell
cd e:\Projects\PowerCOM\Knox\media

# 添加 Vauldy 作为上游 remote
git remote add upstream https://github.com/knoxmedia/Vauldy.git

# 验证
git remote -v
# origin    https://github.com/knoxlab/knox-media.git (fetch/push)
# upstream  https://github.com/knoxmedia/Vauldy.git   (fetch/push)
```


## 3. 分支策略

```
knox-media 本地仓库
├── main              ← 商业版主分支（跟踪 origin/main）
├── community         ← 社区版同步分支（跟踪 upstream/main）
├── feat/xxx          ← 功能开发分支（从 main 拉出）
└── upstream/xxx      ← 待提交到社区版的 PR 分支
```

| 分支 | 跟踪 | 用途 |
| ---- | ---- | ---- |
| `main` | `origin/main` | 商业版开发主线，所有商业功能在此分支开发 |
| `community` | `upstream/main` | 镜像社区版最新代码，用于双向同步 |
| `upstream/<timestamp>` | 临时分支 | 从 community 创建，cherry-pick 商业版改动后提交 PR 给 Vauldy |

**创建 community 分支**：

```powershell
# 拉取社区版代码
git fetch upstream

# 创建本地 community 分支跟踪 upstream/main
git branch community upstream/main
```


## 4. 工作流场景

### 4.1 场景 A：拉取社区版更新到商业版

当 Vauldy 社区版有新的提交时，同步到 knox-media。

```powershell
# 方式一：使用脚本
.\scripts\sync-vauldy.ps1 pull

# 方式二：手动操作
git fetch upstream
git checkout community
git merge upstream/main --no-edit
git checkout main
git merge community --no-edit

# 如有冲突，手动解决后：
git add .
git commit

# 推送到商业版远端
git push origin main
```

**流程图**：

```
upstream/main (Vauldy)
    │
    ▼ git fetch upstream
upstream/main (本地缓存)
    │
    ▼ git merge upstream/main
community (本地)
    │
    ▼ git merge community
main (本地)
    │
    ▼ git push origin main
origin/main (knox-media 远端)
```


### 4.2 场景 B：提交商业版改动给社区版

当 knox-media 中有通用功能改动（非商业专属功能），需要提交 PR 给 Vauldy。

```powershell
# 方式一：使用脚本创建 PR 分支
.\scripts\sync-vauldy.ps1 pr
# 脚本会输出后续步骤提示

# 方式二：手动操作
# 1. 同步社区版最新代码
git fetch upstream
git checkout community
git merge upstream/main --no-edit

# 2. 创建 PR 分支
git checkout -b upstream/20260706-092400

# 3. Cherry-pick 需要提交的商业版改动
git cherry-pick <commit-hash-1>
git cherry-pick <commit-hash-2>

# 4. 推送到 Vauldy（需要有推送权限或使用 Fork）
git push upstream upstream/20260706-092400

# 5. 在 GitHub 上创建 PR
# 访问：https://github.com/knoxmedia/Vauldy/compare/main...knoxlab:knox-media:upstream/20260706-092400
# 填写 PR 标题和描述，提交
```

**流程图**：

```
main (商业版改动 commit A, B, C)
    │
    ▼ git checkout community
community (本地)
    │
    ▼ git merge upstream/main
community (最新)
    │
    ▼ git checkout -b upstream/<ts>
upstream/<ts> (PR 分支)
    │
    ▼ git cherry-pick A, B
upstream/<ts> (含挑选的改动)
    │
    ▼ git push upstream
upstream/<ts> (Vauldy 远端)
    │
    ▼ 创建 PR → main (Vauldy)
Vauldy/main (合并后)
```


### 4.3 场景 C：查看两个仓库的差异

```powershell
# 方式一：使用脚本
.\scripts\sync-vauldy.ps1 diff

# 方式二：手动操作
git fetch upstream
git diff --stat main upstream/main
```


## 5. 同步脚本

脚本路径：`scripts/sync-vauldy.ps1`

| 命令 | 功能 | 说明 |
| ---- | ---- | ---- |
| `.\sync-vauldy.ps1 pull` | 拉取社区版 | 将 Vauldy upstream/main 合并到 knox-media main |
| `.\sync-vauldy.ps1 pr` | 创建 PR 分支 | 创建 upstream/<timestamp> 分支，准备提交给 Vauldy |
| `.\sync-vauldy.ps1 diff` | 查看差异 | 显示 knox-media main 与 Vauldy upstream/main 的文件差异 |


## 6. Cherry-pick 指南

提交 PR 给社区版时，只 cherry-pick 通用功能的 commit，不包含商业专属代码。

**判断标准**：

| 类型 | 示例 | 是否提交给社区版 |
| ---- | ---- | ---------------- |
| Bug 修复 | 修复扫描崩溃、播放器兼容性问题 | 是 |
| 通用功能增强 | 新增刮削源、优化 UI 交互 | 是 |
| 性能优化 | 数据库查询优化、缓存策略 | 是 |
| 依赖升级 | 升级 Gin、React 等依赖 | 是 |
| 预转码功能 | 预转码 Worker、模板管理 | 否（商业专属） |
| License 模块 | 授权校验、功能门控 | 否（商业专属） |
| 企业版 UI | 预转码管理页面、集群监控面板 | 否（商业专属） |

**Cherry-pick 操作**：

```powershell
# 查看 main 分支最近的 commit
git log main --oneline -20

# 切到 PR 分支
git checkout upstream/<timestamp>

# 挑选单个 commit
git cherry-pick <commit-hash>

# 挑选多个连续 commit
git cherry-pick <start-hash>^..<end-hash>

# 如有冲突，手动解决后继续
git add .
git cherry-pick --continue
```


## 7. 冲突处理

当社区版和商业版修改了同一文件时，合并可能产生冲突。

**常见冲突场景**：

| 文件 | 冲突原因 | 处理方式 |
| ---- | -------- | -------- |
| `go.mod` / `go.sum` | 双方都添加了依赖 | 保留两方的依赖，运行 `go mod tidy` |
| `api/router.go` | 双方都添加了路由 | 合并两方路由，商业版路由加 `if enterpriseMod != nil` 判断 |
| `internal/store/db.go` | 双方都添加了迁移 | 合并两方迁移，商业版迁移通过 `RegisterEnterpriseMigration()` 注册 |
| `cmd/server/main.go` | 双方都修改了启动逻辑 | 社区版改动为基础，商业版 `init()` 注入保持不变 |

**冲突解决流程**：

```powershell
# 1. 合并时出现冲突
git merge community
# CONFLICT (content): Merge conflict in api/router.go

# 2. 查看冲突文件
git status

# 3. 手动编辑冲突文件，保留两方改动
# 冲突标记：<<<<<<< / ======= / >>>

# 4. 解决后标记为已解决
git add api/router.go

# 5. 完成合并
git commit
```


## 8. CI/CD 集成

两个仓库各自独立 CI/CD，互不干扰。

**knox-media（商业版）**：

```yaml
# .github/workflows/build.yml
name: Build Enterprise
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.22' }
      - run: go build ./cmd/server
      - run: go test ./...
  release:
    needs: build
    if: startsWith(github.ref, 'refs/tags/')
    steps:
      - run: go build -o knox-media ./cmd/server
      # 发布到私有 Registry
```

**Vauldy（社区版）**：

```yaml
# .github/workflows/build.yml
name: Build Community
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.22' }
      - run: go build ./cmd/server
      - run: go test ./...
```

## 10. 常见问题

### Q1：如何只提交部分改动给社区版？

使用 `git cherry-pick` 挑选特定 commit，不要直接合并 main 分支。

### Q2：社区版更新后，商业版功能会丢失吗？

不会。社区版更新只影响公共代码，商业模块在 knox-media 独立仓库中，通过 `init()` 注入，不受社区版更新影响。

### Q3：如何处理 go.mod 冲突？

两方的 `go.mod` 可能各自添加了不同的依赖。解决方式：保留两方依赖，运行 `go mod tidy` 清理未使用的依赖。

### Q4：提交 PR 给 Vauldy 需要什么权限？

需要对 `knoxmedia/Vauldy` 仓库有推送权限，或者 Fork 后通过 Fork 提交 PR。

### Q5：如何回退错误的社区版合并？

```powershell
# 回退到合并前的状态
git reset --hard HEAD~1

# 或回退到特定 commit
git reset --hard <commit-hash>
```
