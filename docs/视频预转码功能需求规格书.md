## 1. 项目概述

### 1.1 背景

Knox Media 现有的视频转码体系分为三条路径：

- **JIT（Just-In-Time）实时转码**：用户播放时按需转码，延迟感知明显，依赖 CPU/GPU 持续占用。
- **批量转码（Batch Transcode）**：通过 `transcode_task` 表驱动后台 Worker，输出 HLS 多码率自适应流（ABR Ladder），但仅支持单一 HLS 输出格式，且不支持自定义编码参数。
- **分布式转码集群**：基于 `knox-task-center` + Redis 队列 + 多节点 `knox-transcode-service`，支持水平扩容和负载均衡，但当前仅服务于批量转码和 JIT，未接入预转码场景。

三者均无法充分利用服务器空闲时段的 CPU/GPU 算力进行**有计划的、多格式、多清晰度**预转码，导致：

- 用户首次播放新影片时体验不佳（等待 JIT 转码或降级到源文件直出）。
- 无法为不同终端（移动端、桌面端、TV 端）预先准备最适配的输出格式。
- 硬件加速器在空闲时段处于闲置状态，资源浪费。

### 1.2 目标

构建一套**视频预转码系统**（商业版专属），实现：

1. 利用 CPU/GPU 空闲能力，对指定文件或整个媒体库进行预先转码。
2. 「系统选项」中配置**预转码模板**，灵活定义输出格式、清晰度、编码参数。
3. HLS/DASH 输出可选**加密保护**（基本 AES-128 / 私有加密 / DRM 加密）。
4. 转码任务（与既有批量转码统一管理）中可监控每个清晰度级别的独立进度。
5. 播放时自动优先使用已预转码的清晰度，实现秒开。
6. 支持 Webhook 回调，转码完毕时通知外部系统。
7. **支持分布式集群转码**，复用现有 `knox-task-center` + `knox-transcode-service` 集群，通过 Redis 队列分发任务到多个转码节点并行执行，水平扩容加速转码。

### 1.3 术语定义

| 术语                        | 定义                                                    |
| ------------------------- | ----------------------------------------------------- |
| **预转码模板（Preset）**         | 一组转码参数的命名集合，定义输出容器格式、视频编码、音频编码、清晰度梯度、加密方式             |
| **清晰度级别（Rendition）**      | 单个分辨率+码率组合，如 1080p/5Mbps                              |
| **转码任务（Task）**            | 一个源文件应用一个模板后产生的转码工作单元；与既有批量转码共用 `transcode_task` 表，以 `task_type` 区分 |
| **清晰度子任务（Rendition Job）** | 一个预转码任务中某个清晰度级别的独立转码进程，可独立监控进度                        |
| **ABR Ladder**            | 自适应码率阶梯，同一源文件的多个清晰度级别组合                               |
| **HLS AES-128**           | HLS 标准加密，使用 AES-128-CBC 逐段加密，密钥通过 HTTP 下发             |
| **私有加密（PowerDRM）**        | Knox 自研私有加密方案，密钥由 PowerDRM License Server 管理          |
| **DRM 加密（CENC）**          | 基于 Common Encryption 的行业标准 DRM，支持 Widevine / FairPlay |
| **Webhook**               | 转码状态变更时向外部 URL 发送的 HTTP POST 回调                       |

### 1.4 商业版定位与授权

#### 1.4.1 功能归属

视频预转码系统属于 **Knox Media 商业版（Enterprise Edition）** 专属功能，**不纳入社区开源版（Community Edition）**。社区版仅保留既有批量转码（`transcode_task`，`task_type=batch`）能力。

| 维度 | 社区版（Community） | 商业版（Enterprise） |
| ---- | ---------------- | ---------------- |
| 预转码模板管理（系统选项页签） | 不可用 | 可用 |
| 预转码任务（`task_type=pretranscode`） | 不可用 | 可用 |
| 批量转码任务（`task_type=batch`） | 可用 | 可用 |
| 预转码播放集成 | 不可用（降级到 JIT / 直出） | 可用 |
| Webhook 回调 | 不可用 | 可用 |
| 分布式集群转码 | 可用（批量转码） | 可用（批量 + 预转码，共享集群） |
| 加密预转码输出 | 不可用 | 可用 |

社区版用户的播放路径保持不变：**直链 MP4 → 批量转码 HLS → JIT 实时转码 → 源文件直出**。预转码作为额外优化层，仅在商业版中启用。

#### 1.4.2 授权与许可

| 需求 ID | 描述 | 优先级 |
| ------- | ---- | ---- |
| LIC-01 | 预转码功能需要有效的商业版 License Key 才能启用 | P0 |
| LIC-02 | License Key 包含功能模块授权字段（`pretranscode: true`），运行时校验 | P0 |
| LIC-03 | 无授权时，管理界面隐藏预转码相关页签和 API 入口（系统选项页签、转码任务中的预转码创建入口） | P0 |
| LIC-04 | 已创建的预转码任务在授权过期后停止调度，已有输出保留但不提供播放路由 | P0 |
| LIC-05 | License Key 过期前 30 天在管理界面显示续费提醒 | P1 |
| LIC-06 | 支持试用模式：License Key 含 `trial: true` 时，限制最多 10 个文件预转码 | P1 |

**授权验证流程**：

```
管理端/播放端请求
    │
    ├─ 中间件检查 License Key
    │   ├─ 有效 + pretranscode: true → 正常处理
    │   ├─ 有效 + pretranscode: false → 返回 403 Feature Not Licensed
    │   ├─ 即将过期（≤30天） → 正常处理 + 响应 Header 附加过期提醒
    │   └─ 已过期 → 返回 403 License Expired
    │
    └─ 社区版二进制（无 License 模块）→ 路由不存在，404
```

### 1.5 代码模块分离架构

> ⚠️ **架构模型变更说明**：v1.4 采用"Go Module 依赖模型"（knox-media `go.mod require` Vauldy）。该模型与《商业版与社区版双仓库工作流》的 Fork/双 remote 同步模型互斥。v1.5 起统一采用 **Fork 同步模型**，以匹配"便于同步和提交"的目标。详细 Git 操作见 `docs/商业版与社区版双仓库工作流.md`。

#### 1.5.1 仓库定位与同步模型

采用 **社区版公开仓库 + 商业版私有 Fork** 的单代码树双仓库模型：

| 仓库 | GitHub 地址 | 定位 | 许可 |
| ---- | ----------- | ---- | ---- |
| **Vauldy** | `github.com/knoxmedia/Vauldy.git` | 社区版（公开），核心媒体管理 + 批量转码，MIT | MIT |
| **knox-media** | `github.com/knoxlab/knox-media.git` | 商业版（私有），Vauldy 的 Fork + 商业模块（预转码、License 等） | Proprietary |

**同步关系**（详见双仓库工作流文档）：

```
knox-media 本地仓库
├── origin    → github.com/knoxlab/knox-media.git   (商业版，私有)
└── upstream  → github.com/knoxmedia/Vauldy.git     (社区版，公开)

分支：
├── main          ← 商业主分支（社区代码 + 商业模块），跟踪 origin/main
├── community     ← 镜像社区版最新代码，跟踪 upstream/main
├── feat/xxx      ← 功能开发分支（从 main 拉出）
└── upstream/<ts> ← 待提交社区版 PR 分支（从 community 创建，cherry-pick 通用改动）
```

**双向同步方向**：

```
Vauldy (upstream/main)              knox-media (main)
    │                                    │
    │  ── 社区更新合并到商业 ──────────►   │  git merge community → main
    │  (pull: fetch upstream + merge)    │
    │                                    │
    │  ◄── 通用改动提交社区 ────────────  │  cherry-pick 通用 commit → upstream/<ts> → PR
    │  (pr: cherry-pick 非商业专属 commit)│
```

- **正向（社区→商业）**：`git fetch upstream` → `community` 分支合并 `upstream/main` → `main` 合并 `community`。
- **反向（商业→社区）**：仅 cherry-pick **通用功能** commit 到 `upstream/<ts>` 分支，提 PR 给 Vauldy；**商业专属代码永不提交**。

> **模块路径约定**：两仓库共享同一 Go module 路径基线（`github.com/knoxmedia/Vauldy`），商业版 `main` 分支在此基础上叠加商业包。这保证 git merge / cherry-pick 时 import 路径一致，不产生路径重写冲突。商业版二进制产物命名为 `knox-media`，社区版为 `vauldy`。

#### 1.5.2 代码区隔边界（核心）

为满足"便于同步和提交"，商业专属代码必须落在**独立目录**，与社区代码物理隔离，使 cherry-pick 通用 commit 时不会触碰商业代码。

| 路径 | 归属 | 是否提交社区版 | 说明 |
| ---- | ---- | -------------- | ---- |
| `internal/transcode/` | 共享（社区） | 是 | 既有批量转码 + 统一任务调度基座 |
| `internal/coreiface/` | 共享（社区） | 是 | 商业模块可扩展接口定义 + nil 空桩 |
| `internal/jit/` | 共享（社区） | 是 | JIT 实时转码、硬件检测 `hwenc` |
| `internal/store/` | 共享（社区） | 是 | 社区迁移 + `RegisterEnterpriseMigration()` 注册入口 |
| `api/` | 共享（社区） | 是 | 路由注册；商业路由由 `init()` 注入，加 `if enterpriseMod != nil` 守卫 |
| `web/src/` | 共享（社区） | 是 | 社区前端基座；商业页签由注入点挂载 |
| **`internal/pretranscode/`** | **商业专属** | **否** | 预转码模块完整实现（模板、Worker、集群、加密、Webhook） |
| **`internal/license/`** | **商业专属** | **否** | License Key 校验、功能门控中间件 |
| **`web/src/pages/pretranscode/`** | **商业专属** | **否** | 预转码模板页签、Webhook 页签、集群监控子页 |
| **`web/src/components/pretranscode/`** | **商业专属** | **否** | 预转码前端组件（清晰度进度条、加密标识等） |
| `cmd/server/main.go` | 共享骨架 + 商业注入 | 骨架是；注入否 | 社区版 `enterpriseModules = nil`；商业版 `init()` 注入 |
| `internal/store/migrations_pretranscode.go` | **商业专属** | **否** | 通过 `init()` 注册商业迁移 |

**判断标准**（提交 PR 给社区版时）：

| 类型 | 示例 | 提交社区版 |
| ---- | ---- | ---------- |
| Bug 修复 | 修复扫描崩溃、播放器兼容性 | 是 |
| 通用功能增强 | 新增刮削源、优化 UI 交互 | 是 |
| 性能优化 | 数据库查询优化、缓存策略 | 是 |
| 依赖升级 | 升级 Gin、React | 是 |
| 预转码功能 | 预转码 Worker、模板管理 | **否** |
| License 模块 | 授权校验、功能门控 | **否** |
| 企业版 UI | 预转码页签、集群监控 | **否** |

#### 1.5.3 接口契约

接口定义在**共享代码**（`internal/coreiface/`，存在于两仓库）中，供商业版实现；社区版注册 nil 空桩，编译与运行均不依赖商业包。

```go
// internal/coreiface/module.go（共享代码，两仓库都有）
package coreiface

import "context"

// EnterpriseModule 是商业版模块必须实现的通用接口。
// 社区版启动时注册 nil，商业版 init() 注入真实实现。
type EnterpriseModule interface {
    Name() string
    Init(ctx context.Context, deps ModuleDeps) error
    RegisterRoutes(r RouterGroup)
    RegisterWorkers(scheduler WorkerScheduler)
    Shutdown(ctx context.Context) error
}

type ModuleDeps struct {
    DB     *sql.DB
    Config *AppConfig
    Logger *zap.Logger
    Vault  *keystore.Vault
}
```

```go
// internal/coreiface/pretranscode.go（共享代码，两仓库都有）
package coreiface

import "context"

// PretranscodeModule 定义预转码模块的能力契约。
type PretranscodeModule interface {
    EnterpriseModule

    GetPretranscodeStatus(ctx context.Context, fileID string) (*PretranscodeStatus, error)
    GetMasterPlaylist(ctx context.Context, fileID string) (string, error)
    HasPretranscodeOutput(fileID string) bool
    OnMediaDeleted(ctx context.Context, mediaID int64, fileIDs []string) error
}

type PretranscodeStatus struct {
    Available    bool
    PresetName   string
    Renditions   []RenditionStatus
    Encryption   string
    OutputFormat string
}

type RenditionStatus struct {
    Name     string
    Status   string // waiting / running / done / failed
    Progress int
}
```

**社区版入口（Vauldy，空桩注册）**：

```go
// cmd/server/main.go（社区版）

import "github.com/knoxmedia/Vauldy/internal/coreiface"

var enterpriseModules []coreiface.EnterpriseModule  // nil
var pretranscodeMod coreiface.PretranscodeModule     // nil

func main() {
    // ... 正常启动逻辑
    for _, mod := range enterpriseModules {  // 空循环
        mod.Init(ctx, deps)
        mod.RegisterRoutes(router)
    }
    // 播放决策：pretranscodeMod == nil → 跳过预转码，走 JIT/直出

```

**商业版入口（knox-media main，init 注入）**：

```go
// cmd/server/main.go（商业版，仅 main 分支）
package main

import (
    "github.com/knoxmedia/Vauldy/internal/coreiface"
    "github.com/knoxmedia/Vauldy/internal/license"
    "github.com/knoxmedia/Vauldy/internal/pretranscode"
)

func init() {
    coreiface.EnterpriseModules = []coreiface.EnterpriseModule{
        license.NewModule(),
        pretranscode.NewModule(),
    }
    coreiface.PretranscodeMod = pretranscode.NewModule()
}

func main() {
    coreiface.Main() // 复用社区版启动逻辑，商业模块已通过 init() 注入
}
```

> 注：`cmd/server/main.go` 是共享骨架文件，社区版与商业版均存在。社区版仅有空桩；商业版在 `init()` 中注入。merge 社区更新时，此文件是常见冲突点，按工作流文档第 7 节处理（社区改动为基础，商业 `init()` 注入保持不变）。

#### 1.5.4 数据库迁移隔离

社区迁移与商业迁移分离注册，社区版二进制不含商业表：

```go
// internal/store/migrations.go（共享代码）
var enterpriseMigrations []Migration

func RegisterEnterpriseMigration(m Migration) {
    enterpriseMigrations = append(enterpriseMigrations, m)
}

func RunMigrations(db *sql.DB) error {
    all := communityMigrations                // 社区迁移（含 transcode_task）
    all = append(all, enterpriseMigrations...) // 追加商业迁移（仅商业版 init() 注册）
    return runAll(db, all)
}
```

```go
// internal/store/migrations_pretranscode.go（商业专属，仅 main 分支）
package store

func init() {
    store.RegisterEnterpriseMigration(Migration{
        ID: "00XX_create_pretranscode_tables",
        Up: func(db *sql.DB) error {
            // CREATE TABLE transcode_preset ...
            // CREATE TABLE preset_rendition ...
            // CREATE TABLE pretranscode_task_meta ...   ← 扩展表，不修改 transcode_task
            // CREATE TABLE pretranscode_rendition_job ...
            // CREATE TABLE pretranscode_webhook ...
            // CREATE TABLE pretranscode_webhook_log ...
            return nil
        },
    })
}
```

> **关键约束**：预转码不复用、不修改社区 `transcode_task` 表结构。预转码特有字段（preset_id、encryption_mode 等）存放于扩展表 `pretranscode_task_meta`（见 4.3），通过 `task_id` 外键关联。这保证社区迁移与商业迁移物理隔离，merge 零冲突。

#### 1.5.5 前端隔离

前端采用"社区基座 + 商业注入点"模式：

```

├── pages/                      ← 社区页面
├── components/                 ← 社区组件
├── i18n/                       ← 多语言
└── enterprise/                 ← 商业注入入口（空壳，社区版为空）
    ├── tabs/                   ← 系统选项商业页签挂载点

web/src/pages/pretranscode/     （商业专属，仅 main 分支）
web/src/components/pretranscode/（商业专属，仅 main 分支）
```

#### 3.2.2 任务触发

| TASK-02 | 对整个媒体库批量触发预转码（选择模板，可选筛选条件：未转码的、新增的）  | P0  |

| 需求 ID  | 描述                                    | 优先级 |
| ------ | ------------------------------------- | --- |
| SCH-01 | 并发控制：管理员可配置最大同时转码任务数（区分 CPU/GPU）      | P0  |
| SCH-02 | 空闲检测：当 CPU 使用率低于阈值时自动启动排队任务           | P1  |
| SCH-03 | 播放优先：当用户发起播放请求时，可暂停/降低预转码任务优先级，保障播放流畅 | P0  |
| SCH-04 | 任务排队：超出并发限制的任务进入等待队列，按优先级和创建时间排序      | P0  |
| SCH-05 | 断点续转：转码中断后（进程崩溃/重启），可从上次完成的分片处继续      | P1  |

#### 3.2.4 清晰度子任务进度监控（预转码专属）

| 需求 ID   | 描述                                                           | 优先级 |
| ------- | ------------------------------------------------------------ | --- |
| PROG-01 | 每个清晰度级别有独立的进度百分比（0-100）                                      | P0  |
| PROG-02 | 任务整体进度 = 所有清晰度子任务进度的加权平均                                     | P0  |
| PROG-03 | 每个清晰度子任务状态独立管理：waiting → running → done / failed / cancelled | P0  |
| PROG-04 | 已完成的清晰度立即可用（无需等待所有清晰度全部完成）                                   | P0  |
| PROG-05 | 失败的清晰度子任务不影响其他清晰度继续转码                                        | P0  |
| PROG-06 | 转码任务详情页（预转码类型）展示每个清晰度的独立进度条和状态                               | P0  |

**进度计算方式**：

```
清晰度子任务进度 = (已编码时长 / 源文件总时长) × 100
任务整体进度 = Σ(各清晰度子任务进度) / 清晰度总数
```

| 需求 ID  | 描述                                       | 优先级 |
| ------ | ---------------------------------------- | --- |
| ACT-01 | 取消任务：停止所有清晰度子任务的 FFmpeg 进程，标记为 cancelled | P0  |
| ACT-02 | 重试任务：对失败的清晰度子任务重新排队                      | P0  |
| ACT-03 | 删除任务：删除任务记录及已生成的输出文件                     | P0  |
| ACT-04 | 暂停/恢复任务：暂停排队中的任务，恢复后重新入队                 | P0  |
| ACT-05 | 清理失败任务：批量清理超过指定天数的失败任务记录和文件              | P0  |

#### 3.2.6 分布式集群转码（共享基础设施）

预转码与批量转码共享同一 `knox-task-center` + `knox-transcode-service` 集群，通过独立 Redis 队列前缀互不阻塞。

| 需求 ID  | 描述                                                                  | 优先级 |
| ------ | ------------------------------------------------------------------- | --- |
| CLS-01 | 预转码任务支持通过 Redis 队列分发到 `knox-transcode-service` 集群节点执行               | P0  |
| CLS-02 | 任务中心负责负载均衡，将清晰度子任务均匀分配到空闲转码节点                                       | P0  |
| CLS-03 | 每个清晰度子任务独立分发，不同清晰度可在不同节点并行转码                                        | P0  |
| CLS-04 | 转码节点无状态，支持水平扩容：新增节点即刻参与任务分配                                          | P0  |
| CLS-05 | 转码节点支持硬件检测上报：节点启动时注册可用硬件编码器，任务中心按硬件能力分配任务                            | P0  |
| CLS-06 | 节点宕机自动故障转移：心跳超时后，任务中心将该节点 running 状态的任务重新入队                         | P0  |
| CLS-07 | 进度实时回调：转码节点通过 HTTP 回调或 WebSocket 向媒体服务上报每个清晰度子任务的进度                  | P0  |
| CLS-08 | 集群模式与单机模式可切换：配置 `cluster.enabled=false` 时退化为本地 Worker 单机执行          | P0  |
| CLS-09 | 转码节点通过共享存储（NFS/SMB/OSS）访问源文件和写入输出文件，不传输二进制流                         | P0  |
| CLS-10 | 「转码任务 → 集群监控」子页展示集群状态：各节点在线状态、当前任务数、硬件利用率、队列深度                      | P0  |

**集群转码流程**：

```
管理员触发预转码
    │
    ├─ media-service 在 transcode_task 创建任务 + pretranscode_task_meta 写元数据
    │   + N 个 pretranscode_rendition_job
    │
    ├─ 对每个 waiting 状态的 rendition_job：
    │   ├─ 序列化为任务消息（file_id, preset, rendition, storage_path, encryption_mode）
    │   ├─ 推入 Redis 队列：pretranscode:queue:{priority}
    │   └─ 状态更新为 queued
    │
    ├─ knox-transcode-service 节点监听队列
    │   ├─ 抢占任务（Redis BRPOP / 分布式锁）
    │   ├─ 检查硬件编码器可用性 → 选择最优编码器
    │   ├─ 拉取源文件（NFS/SMB/OSS/HTTP）
    │   ├─ 执行 FFmpeg 转码 + 可选加密
    │   ├─ 实时回调进度 → media-service
    │   └─ 完成后回调 → 更新 rendition_job 状态 + 输出路径
    │
    └─ 所有 rendition_job 完成 → 更新 transcode_task 状态 → 触发 Webhook
```

**集群 vs 单机模式配置**：

```yaml
pretranscode:
  mode: cluster          # cluster | standalone
  cluster:
    redis:
      host: 127.0.0.1
      port: 6379
      queue_prefix: pretranscode     # 与 transcode:queue 区分
    task_center_url: http://localhost:9100
    callback_url: http://localhost:8900/api/v1/admin/transcode/callback
    heartbeat_interval: 10s
    node_timeout: 60s
  standalone:
    max_concurrent_cpu: 4
    max_concurrent_gpu: 2
```

```

    │
    ├─ 检查媒体库「启用预转码」配置
    │   ├─ 未启用 → 结束
    │   └─ 已启用 → 继续
    │
    ├─ 收集待预转码文件列表
    │   ├─ 「仅新增文件」= true → 仅本次扫描新增的视频文件

    │   ├─ 扫描完成后立即 → 立即创建任务
    │   ├─ 空闲时段 → 等待系统空闲（CPU < 阈值）时创建任务
    │   └─ 手动确认 → 发送通知，等待管理员确认后创建任务
    │
    ├─ 系统性能检测（自动触发场景）
    │   ├─ CPU 使用率 > 80% → 延迟触发，进入等待队列

    │
    └─ 批量创建预转码任务
        ├─ 每个文件创建独立任务（便于独立管理和取消）
        ├─ 使用媒体库配置的默认模板

```

## 4. 数据模型

> **区隔原则**：`transcode_task` 为社区既有表，**不做任何结构修改**；预转码特有字段全部落入商业扩展表 `pretranscode_task_meta`，通过 `task_id` 外键关联。模板、Webhook 表为商业专属。

### 4.1 预转码模板表（`transcode_preset`）— 商业专属

| 字段                  | 类型                  | 说明                                                                                  |
| ------------------- | ------------------- | ----------------------------------------------------------------------------------- |
| `id`                | INTEGER PK          | 主键                                                                                  |
| `name`              | TEXT NOT NULL       | 模板名称，如 "HLS-标准"                                                                     |
| `description`       | TEXT                | 模板描述                                                                                |
| `output_format`     | TEXT NOT NULL       | 输出格式：`hls` / `mp4` / `dash` / `flv`                                                 |
| `encryption_mode`   | TEXT DEFAULT 'none' | 加密模式：`none` / `aes128` / `powerdrm` / `drm`                                         |
| `video_codec`       | TEXT NOT NULL       | 视频编码器：`libx264` / `libx265` / `h264_nvenc` / `h264_qsv` / `h264_amf` / `h264_vaapi` |
| `video_preset`      | TEXT                | x264/x265 preset，如 `veryfast`                                                       |
| `video_crf`         | INTEGER             | CRF 值，0-51                                                                          |
| `video_maxrate`     | TEXT                | 最大码率，如 `5000k`                                                                      |
| `video_bufsize`     | TEXT                | 缓冲区大小，如 `10M`                                                                       |
| `video_profile`     | TEXT                | 编码 profile：`baseline` / `main` / `high`                                             |
| `video_gop`         | INTEGER             | GOP 大小（秒）                                                                           |
| `video_pix_fmt`     | TEXT                | 像素格式，默认 `yuv420p`                                                                   |
| `audio_codec`       | TEXT NOT NULL       | 音频编码器：`aac` / `mp3` / `copy`                                                        |
| `audio_bitrate`     | TEXT NOT NULL       | 音频码率，如 `128k`                                                                       |
| `audio_channels`    | INTEGER             | 声道数，默认 2                                                                            |
| `audio_sample_rate` | INTEGER             | 采样率，默认 48000                                                                        |
| `hw_fallback`       | INTEGER             | 硬件编码失败时是否回退到 libx264，1=是                                                            |
| `is_builtin`        | INTEGER             | 是否内置模板（不可删除），1=是                                                                    |
| `is_enabled`        | INTEGER             | 是否启用，默认 1                                                                           |
| `sort_order`        | INTEGER             | 排序权重                                                                                |
| `created_at`        | TIMESTAMP           | 创建时间                                                                                |
| `updated_at`        | TIMESTAMP           | 更新时间                                                                                |

> **约束**：当 `output_format` 为 `mp4` 或 `flv` 时，`encryption_mode` 强制为 `none`。

## 6. FFmpeg 命令构建规则

### 6.1 HLS 输出

```
ffmpeg -y -hide_banner -nostats -loglevel error \
  -i <input> \
  -map 0:v:0 -map 0:a:0? \
  -c:v <video_codec> -preset <preset> -crf <crf> \
  -b:v <video_bitrate> -maxrate <maxrate> -bufsize <bufsize> \
  -vf scale=-2:<height> \
  -c:a <audio_codec> -b:a <audio_bitrate> -ac <channels> \
  -f hls \
  -hls_time 4 \
  -hls_playlist_type vod \
  -hls_segment_filename <out>/<name>_%03d.ts \
  <out>/<name>.m3u8
```

### 6.2 MP4 输出

```
ffmpeg -y -hide_banner -nostats -loglevel error \
  -i <input> \
  -map 0:v:0 -map 0:a:0? \
  -c:v <video_codec> -preset <preset> -crf <crf> \
  -b:v <video_bitrate> -maxrate <maxrate> -bufsize <bufsize> \
  -vf scale=-2:<height> \
  -c:a <audio_codec> -b:a <audio_bitrate> -ac <channels> \
  -movflags +faststart \
  <out>/<name>.mp4
```

### 6.3 DASH 输出

```
ffmpeg -y -hide_banner -nostats -loglevel error \
  -i <input> \
  -map 0:v:0 -map 0:a:0? \
  -c:v <video_codec> -preset <preset> -crf <crf> \
  -b:v <video_bitrate> -maxrate <maxrate> -bufsize <bufsize> \
  -vf scale=-2:<height> \
  -c:a <audio_codec> -b:a <audio_bitrate> -ac <channels> \
  -f dash \
  -seg_duration 4 \
  -adaptation_sets "id=0,streams=v id=1,streams=a" \
  <out>/<name>_init.mp4 \
  <out>/<name>_$Number$.m4s \
  <out>/manifest.mpd
```

### 6.4 FLV 输出

```
ffmpeg -y -hide_banner -nostats -loglevel error \

### 6.5 HLS AES-128 加密输出

```
# 1. 生成密钥文件
openssl rand 16 > <out>/enc.key
echo "http://<host>/api/v1/drm/hls-key/<task_id>" > <out>/enc.keyinfo
echo "<out>/enc.key" >> <out>/enc.keyinfo
openssl rand -hex 16 >> <out>/enc.keyinfo

# 2. FFmpeg 加密转码
ffmpeg -y -hide_banner -nostats -loglevel error \
  -i <input> \
  -map 0:v:0 -map 0:a:0? \
  -c:v <video_codec> -preset <preset> -crf <crf> \
  -b:v <video_bitrate> -maxrate <maxrate> -bufsize <bufsize> \

## 8. 系统集成

### 8.1 与现有转码系统的关系（合并后）

| 维度      | 批量转码（`task_type=batch`） | 预转码（`task_type=pretranscode`） |
| ------- | ------------------------- | ------------------------------ |
| 任务表    | `transcode_task`（社区）       | `transcode_task` + `pretranscode_task_meta`（商业扩展） |
| 任务管理 UI | 任务管理 → 转码任务（统一列表）         | 同左，type=pretranscode 筛选        |
| 模板      | 无（硬编码 Rendition 梯度）       | `transcode_preset` + `preset_rendition` |
| 输出格式    | 仅 HLS                     | HLS / MP4 / DASH / FLV         |
| 清晰度进度   | 整体进度                      | 每个清晰度独立进度（`pretranscode_rendition_job`） |
| 加密      | 仅 JIT 加密                  | AES-128 / PowerDRM / DRM CENC  |
| Webhook | 无                         | 支持                             |
| 编码参数    | 固定（veryfast + CRF 23）     | 可配置                            |
| 分布式集群   | 支持（`knox-task-center`）    | 支持（同一集群，独立 Redis 队列前缀）         |
| 归属      | 社区 + 商业均可用                | 商业专属                           |

两者**统一管理、并行运行**。预转码通过扩展表叠加在 `transcode_task` 之上，不修改社区表结构，社区代码零侵入。预转码与批量转码共享同一分布式集群，通过独立 Redis 队列前缀（`pretranscode:queue:`* vs `transcode:queue`）互不阻塞。

### 8.2 加密系统集成

预转码加密复用现有 Knox 加密基础设施：

| 组件                               | 复用方式                           |
| -------------------------------- | ------------------------------ |
| `internal/keystore`              | AES-128 密钥生成与存储                |
| `internal/drm`                   | Widevine / FairPlay License 签发 |
| `internal/transcode/powerdrm.go` | PowerDRM Manifest 重写           |
| `api/handler/drm.go`             | License / 密钥服务端点               |
| `drm_asset` 表                    | 加密资产注册                         |
| `drm_key_material` 表             | 密钥材料存储                         |

**加密工作流**：

1. Worker 转码完成后，根据模板 `encryption_mode` 调用对应加密流程。
2. `aes128`：生成密钥 → 写入 `enc.key` + `enc.keyinfo` → FFmpeg `-hls_key_info_file` 一步完成。
3. `powerdrm`：FFmpeg 输出明文 → `powerdrm.go` 重写 Manifest → 注册到 `drm_asset`。
4. `drm`：FFmpeg 输出明文 fMP4 → Shaka Packager CENC 加密 → 注册到 `drm_asset` + `drm_key_material`。

### 8.3 分布式集群集成

预转码系统复用现有 `knox-task-center` + `knox-transcode-service` 分布式集群基础设施：

| 组件                       | 复用方式                                            |
| ------------------------ | ----------------------------------------------- |
| `knox-task-center`       | 预转码任务入队、负载均衡、节点管理、故障转移                          |
| `knox-transcode-service` | 执行 FFmpeg 转码 + 加密，多节点并行                         |
| Redis                    | 任务队列（`pretranscode:queue:{priority}`）、分布式锁、进度缓存 |
| NFS/SMB/OSS              | 共享存储：源文件读取、输出文件写入                               |
| HTTP 回调                  | 转码节点 → media-service：进度上报、状态更新                  |

**集群模式下的任务分发粒度**：

- **单文件 + 单模板** → 产生 N 个清晰度子任务（rendition_job）
- 每个 rendition_job 独立入队 Redis，可被不同节点并行消费
- 同一源文件的不同清晰度可在不同节点同时转码，**充分利用集群算力**
- 不同源文件的任务完全独立，天然支持集群并行

**节点硬件能力感知**：

- 转码节点启动时向 `knox-task-center` 注册硬件编码器信息（NVENC/QSV/AMF/VAAPI）
- 任务中心根据模板 `video_codec` 字段匹配具备对应硬件的节点
- 若模板要求 `h264_nvenc`，任务中心优先分配到有 NVENC 的节点
- 若无匹配硬件节点可用，可分配到 CPU 节点并自动回退到 `libx264`

### 8.4 硬件编码器复用

复用现有 `internal/jit/hwenc` 包的硬件检测能力：

- `hwenc.DetectAll()` 自动检测可用的硬件编码器
- 模板配置的 `video_codec` 字段接受硬件编码器 ID
- Worker 执行时自动回退到 libx264（如果硬件编码失败）

## 9. 非功能需求

### 9.1 性能

| 指标                           | 要求                    |
| ---------------------------- | --------------------- |
| 任务创建响应                       | ≤ 200ms               |
| 进度轮询响应                       | ≤ 100ms               |
| 1080p 转码速度（NVENC）            | ≥ 300fps（约 12x 实时）    |
| 1080p 转码速度（libx264 veryfast） | ≥ 100fps（约 4x 实时）     |
| 并发任务数（单机模式）                  | 可配置，默认 2（GPU）/ 4（CPU） |
| 集群任务分发延迟                     | ≤ 500ms（从入队到节点开始执行）   |
| 集群节点故障转移时间                   | ≤ 60s（心跳超时 + 任务重入队）   |

### 9.2 可靠性

- 单个清晰度子任务失败不影响其他清晰度
- 进程崩溃后，running 状态的任务自动标记为 failed（启动时清理）
- 输出文件完整性校验（检查 master.m3u8 / .mp4 文件存在且大小 > 0）
- **集群模式**：转码节点宕机后，任务中心自动将 running 任务重新入队分配到其他节点
- **集群模式**：Redis 队列持久化（AOF），任务消息不丢失

### 9.3 存储

- 预转码输出与源文件存储分离（独立目录）
- 支持存储空间预警（配置阈值，超过时停止新建任务）
- 支持 LRU 清理策略（可选，优先清理最久未播放的预转码输出）

| AC-41 | 扫描完成自动预转码   | 媒体库扫描完成后，根据配置自动为新增视频创建预转码任务                 |
| AC-42 | 性能自适应调度     | CPU > 80% 时暂停创建任务，有播放请求时降低预转码优先级               |
| AC-43 | 优化管理页面列表   | 优化管理页正确显示所有已优化视频，支持搜索、筛选、排序、分页               |
| AC-44 | 优化管理批量操作   | 可多选视频并批量移除优化输出，确认对话框提示释放空间大小                 |
| AC-45 | 优化管理存储统计   | 页面顶部正确显示已优化视频数、清晰度数、占用空间、可释放空间               |
| AC-46 | 媒体库配置隔离     | 媒体库预转码配置字段仅在商业版迁移中添加，社区版 `media_library` 表不变    |

## 11. 实施计划

### 阶段零（P0 基础设施 — 模块分离与同步基线）

- Vauldy `internal/coreiface/` 定义 `EnterpriseModule` + `PretranscodeModule` 接口（两仓库共有）
- Vauldy `cmd/server/main.go` 注册空桩（商业模块 nil，播放降级到 JIT/直出）
- knox-media `main` 分支建立 `internal/pretranscode/`、`internal/license/` 商业专属目录
- knox-media `cmd/server/main.go` 通过 `init()` 注入商业模块
- 配置双 remote（origin/upstream）、`community` 分支，跑通 `sync-vauldy.ps1`（见工作流文档）
- 数据库迁移通过 `RegisterEnterpriseMigration()` 注册，社区版不含
- 双仓库 CI/CD 流水线：Vauldy 产出 `vauldy`，knox-media 产出 `knox-media`

### 阶段一（P0 核心）

- 数据库表创建（模板 + 扩展表 + 子任务 + Webhook 表，均商业迁移）
- 系统选项「预转码模板」页签 + 模板 CRUD API（含加密模式配置）
- 预转码 Worker（HLS + MP4 格式，libx264）
- **HLS AES-128 加密转码**（密钥生成 + FFmpeg key_info_file）
- 任务管理→转码任务统一列表（batch + pretranscode），单文件任务创建 + 清晰度子任务进度
- **本地模式**：单机 Worker 顺序执行
- 播放集成（预转码优先 + 加密模式路由）
- 前端：系统选项模板页签 + 转码任务页预转码创建/监控
- **License Key 授权校验中间件**（运行时功能门控）
- **上传时预转码**：上传组件增加预转码开关和模板选择，上传完成后自动创建任务
- **单视频优化管理**：视频更多菜单增加「优化」选项，弹出对话框查看/移除/再次优化

### 阶段二（P1 增强）

- DASH / FLV 输出格式
- **PowerDRM 私有加密**（HLS/DASH）
- **DRM CENC 加密**（Shaka Packager 集成）
- 硬件编码器支持 + 自动回退
- 批量转码 + 媒体库级触发
- **集群模式**：Redis 队列分发 + `knox-transcode-service` 多节点并行
- **集群模式**：节点故障转移 + 硬件能力感知调度
- 系统选项「预转码 Webhook」页签 + 完整 Webhook 回调
- 空闲检测 + 播放优先调度
- 前端增强（清晰度进度条、加密状态标识、Webhook 发送日志、**集群监控子页**）
- **媒体库扫描预转码**：媒体库设置增加预转码配置，扫描完成后根据性能自动触发
- **优化管理页面**：管理菜单增加优化管理，显示已优化视频列表，支持查看/移除/批量清理/存储统计

### 阶段三（P2 优化）

- 定时触发 + 负载检测
- 断点续转
- 存储空间预警 + LRU 清理
- 模板克隆
- Webhook HMAC 签名 + 发送日志
- 集群节点排空（drain）运维操作
- 跨节点转码性能统计与分析
- **性能自适应调度优化**：CPU 阈值动态调整、播放优先级智能降级
- **优化管理增强**：按格式/模板分布图表、存储趋势分析
